# 岗位判定可视化大屏 —— 设计文档

日期:2026-09-24
状态:待评审
关联:`docs/superpowers/specs/2026-09-14-boss-ai-gate-design.md`(判定服务本体)

## 1. 背景与目标

判定服务(`boss-ai-gate`)对每个岗位给出"投/不投"及理由,并生成招呼语;油猴脚本据此执行。**但目前没有任何地方能看到"整体在发生什么"**:服务端只读不写、不落盘;脚本的记录存在浏览器 IndexedDB 里,要导出得手动点按钮。

本设计新增一个**可视化大屏**:实时展示每个岗位的判定与执行结果,并把记录**追加落盘**到文件。

### 成功标准

1. 运行期间能在一个独立窗口里实时看到每个岗位的:公司、规模、岗名、地点、薪资、判定、实际结果、理由或话术。
2. 所有记录持久化到文件,跨运行累积,不丢历史。
3. 能区分"本轮"与"累计"。
4. 能导出 CSV 供 Excel 分析。
5. **上报绝不能影响脚本的既有行为** —— 判定、跳过、发送的逻辑与结果一字不变。

### 关键约束

- 沿用 `boss-ai-gate` 既有约定:**零第三方依赖**、ESM、中文注释、`node:test`。
- 沿用 userscript 既有约定:**单文件、无构建、无依赖**。
- 数据来源分散(见第 2 节),这是本设计的核心约束。

## 2. 数据流与组件

现有数据分布:

| 数据 | 位置 | 谁有 |
|---|---|---|
| 公司名/规模/行业/岗名/地点/薪资 | 脚本(IndexedDB)+ 发给服务的请求体 | 两者 |
| 判定结果 + 理由 + 生成的话术 | 服务端 `/evaluate` 的响应 | 只有服务端 |
| **实际是否发出** | 脚本 | **只有脚本** |

**没有任何单一位置持有完整信息。** 因此由**脚本在流程终点组装整行**并上报 —— 因为判定结果本来就是 `/evaluate` 的返回值,脚本同时握着两头。

```
脚本流程终点
  ├ 岗位信息(flattenJob)
  ├ 判定结果(/evaluate 响应)
  └ 实际结果(发送成功 / 跳过)
        │ POST /report
        ▼
服务端
  ├ data/jobs.jsonl          追加落盘(唯一真实来源)
  └ 内存记录数组(启动时从文件加载 + 运行中追加)
        │
        ├ GET /dashboard             看板页面(HTML)
        ├ GET /api/records?since=N    增量轮询
        └ GET /api/export.csv         CSV 导出
        ▼
独立窗口:chrome --app=http://127.0.0.1:8787/dashboard
```

服务端保持"哑":**只追加、不判断**。业务逻辑仍在判定引擎与脚本里。

### 组件划分

| 组件 | 职责 | 依赖 |
|---|---|---|
| `src/ledger.js`(新) | 记录存储:追加写、增量读、汇总、CSV 序列化 | 仅 `node:fs` |
| `src/dashboard.js`(新) | 看板页面的 HTML/CSS/JS(内联返回) | 无 |
| `src/server.js`(改) | 新增 4 条路由,把 ledger 接上 | 以上两者 |
| `zhipin-auto-greeting.user.js`(改) | 在终态组装并上报 | 无新增 |

## 3. 记录契约

一行 = 一个岗位的一次终态。字段:

```json
{
  "at": "2026-09-24T15:04:05.123Z",
  "runId": "2026-09-24T14:50:11.000Z",
  "company": "中科飞测",
  "companyScale": "1000-9999人",
  "companyIndustry": "半导体设备",
  "jobName": "软件测试工程师-校招-广州-00429",
  "city": "广州",
  "address": "广州·黄埔区·九佛",
  "salary": "20-30K",
  "stage": "sent",
  "verdict": true,
  "reason": "城市:广州(白名单);公司:...;职位:...;薪资:...",
  "greeting": "你好，我是示例大学张三，做过...",
  "variant": "cpp"
}
```

字段语义:

| 字段 | 类型 | 说明 |
|---|---|---|
| `at` | ISO 字符串 | 上报时刻 |
| `runId` | ISO 字符串 | **服务进程启动时刻**,作为"本轮"的标识 |
| `company` / `companyScale` / `companyIndustry` | string | 缺则空串 |
| `jobName` / `city` / `address` / `salary` | string | 同上 |
| `stage` | `"sent"` \| `"skipped"` | **实际结果** |
| `verdict` | `true` \| `false` \| `null` | **服务判定**;`null` = **没有判定结论** —— 包括"未走到判定"(黑名单/已沟通/无沟通按钮等前置环节跳过)与"走到了但判定服务不可用"两种情况。两者由 `reason` 文案区分,不额外加字段 |
| `reason` | string | 判定理由或跳过原因 |
| `greeting` | string | 沟通话语;未发送时为空串 |
| `variant` | string | 选中的简历版本;未判定时为空串 |

**`stage` 与 `verdict` 必须独立记录。** 两者组合能暴露关键异常:

| verdict | stage | 含义 |
|---|---|---|
| true | sent | 正常投递 |
| true | **skipped** | **判定投了却没发出去** ← 最值得关注的失败 |
| false | skipped | 正常跳过 |
| null | skipped | 前置环节跳过,没走判定 |

## 4. 服务端接口

### `POST /report`

请求体即第 3 节的一行记录(缺字段的服务端补空串)。响应 `{ ok: true, seq: <number> }`。

- 追加写 `data/jobs.jsonl`(一行一个 JSON,`\n` 结尾)
- 同时推入内存数组
- **写入失败返回 500,但不抛出到进程** —— 服务端不能因为磁盘问题崩掉

### `GET /api/records?since=<seq>`

返回 `{ runId, seq, stats: {...}, records: [...] }`

**`seq` 的定义:** 一条记录在**文件顺序中的位置 + 1**(即第 1 行是 1,第 2 行是 2)。服务启动时从已加载的行数继续递增,**不重置** —— 这样服务重启后,页面持有的 `since` 仍然有效,不会因为 seq 归零而重复拉取或漏拉。

- `since` 省略、为 0 或非法时返回全部;否则只返回 `seq` 大于该值的记录
- `records` 里每条附带其 `seq`
- `stats` 见下

`stats` 结构:

```json
{
  "current": { "judged": 0, "sent": 0, "skipped": 0, "anomaly": 0 },
  "total":   { "judged": 0, "sent": 0, "skipped": 0, "anomaly": 0 }
}
```

- `current` 只统计 `runId === 本次进程启动时刻` 的记录;`total` 统计全部
- `judged` = `verdict !== null` 的条数
- `sent` = `stage === "sent"` 的条数
- `skipped` = `stage === "skipped"` 的条数
- `anomaly` = `verdict === true && stage === "skipped"` 的条数

### `GET /api/export.csv`

返回 CSV(UTF-8 **带 BOM**,否则 Excel 打开中文会乱码)。表头为第 3 节的字段名。字段值按 RFC 4180 转义(含逗号/引号/换行时用双引号包裹,内部引号翻倍)。

### `GET /dashboard`

返回看板页面 HTML(`text/html; charset=utf-8`)。

## 5. 看板页面

布局:

```
┌──────────────────────────────────────────────────────────┐
│ 已判定 128 │ 已沟通 96 │ 已跳过 32 │ 发送异常 3            │
│ [本轮] [累计]                              [导出 CSV]     │
├──────────────────────────────────────────────────────────┤
│ 时间  公司  规模  岗位  地点  薪资  判定  实际  理由/话术   │
│ 15:04 中科飞测 1000-9999 … 广州 20-30K ✅ 已发  …          │
│ …（新记录从顶部插入,实时刷新）                              │
└──────────────────────────────────────────────────────────┘
```

- **纯原生** HTML/CSS/JS,内联在 `dashboard.js` 里;不引入任何 CDN 或框架(与项目零依赖约定一致)
- **轮询**:每 1.5 秒 `GET /api/records?since=<本地最大 seq>`;只渲染新增行(追加到表格顶部),避免整表重绘
- **本轮/累计切换**:切换后重置本地 `since` 并全量重绘
- 「理由/话术」列宽度受限,悬停显示全文(用 `title` 属性即可,不引入 tooltip 库)
- 空状态、服务不可达时显示明确提示,不白屏
- 表格行数超过 500 时只保留最近 500 行在 DOM 里(数据仍在文件与内存中)

## 6. 脚本侧上报

新增一个 helper:

```js
const Ledger = {
  // 尽力而为:不 await、不抛出、失败只记日志。
  // 上报永远不能影响主流程 —— 判定服务挂了也不该拖慢脚本。
  report(job, outcome) { ... }
};
```

`outcome = { stage, reason, greeting }`,其余字段由 `flattenJob(job)` 提供。

### 上报点 = 所有终态

| 位置 | stage | reason 来源 | verdict |
|---|---|---|---|
| 聊天页发送成功 | `sent` | —— | `true` |
| AI 闸门判定不投 | `skipped` | `verdict.reason` | `false` |
| AI 判定服务不可用 | `skipped` | `verdict.reason` | `null` |
| 无沟通按钮 | `skipped` | 固定文案 | `null` |
| 公司黑名单命中 | `skipped` | 黑名单规则 | `null` |
| Boss 活跃度不匹配 | `skipped` | 固定文案 | `null` |
| 页面显示已沟通 | `skipped` | 固定文案 | `null` |
| 本地记录已沟通 | `skipped` | 固定文案 | `null` |
| 公司筛选不匹配 | `skipped` | 固定文案 | `null` |

`verdict` 与 `variant` 只在走过 AI 闸门的分支才有值,其余为 `null` / 空串。

### 三条硬约束

1. **绝不阻塞主流程。** 不 `await`;`GM_xmlhttpRequest` 的 `onerror`/`ontimeout` 只写 `logDebugEvent`,不改变控制流。
2. **绝不影响既有行为。** 上报失败不得改变任何判定、跳过、发送的结果或顺序。上报调用插在既有 `Database.saveJobRecord` 之后,与其并列,不改动它。
3. **不含简历内容。** 上报体只含岗位信息、判定理由、招呼语。简历全文不进上报。

## 7. 文件与窗口

- 数据文件:`boss-ai-gate/data/jobs.jsonl`。目录不存在时由服务端自动创建。
- `.gitignore` 追加 `data/`。
- 打开窗口:项目根目录放 `打开大屏.cmd`,内容为
  ```
  start chrome --app=http://127.0.0.1:8787/dashboard
  ```
  `--app` 模式无地址栏、无标签页,可固定到任务栏。
- 服务端支持可选参数 `--open-dashboard`:启动时自动弹窗。**默认不开启**,避免每次重启都弹。

## 8. 错误处理

| 情况 | 处理 |
|---|---|
| `data/` 目录不存在 | 启动时自动创建 |
| JSONL 里某行损坏(手动编辑/写一半) | 跳过该行并记 warn,**不阻止服务启动** |
| 磁盘写失败 | `/report` 返回 500;内存记录仍追加(页面仍能看到);服务不崩 |
| 脚本上报失败(服务未启动) | 静默,只写 `logDebugEvent`;主流程不受影响 |
| 看板轮询失败 | 页面显示"连接中断",继续按 1.5 秒重试 |
| `since` 传了非法值 | 当作 0(返回全量) |

## 9. 测试

| 层 | 方式 |
|---|---|
| `ledger.js` | 纯单测:追加后能读回;增量读按 seq 正确切片;`stats` 的四类计数(含 `anomaly` 的 `verdict && skipped` 组合);CSV 转义(逗号/引号/换行/中文);损坏行被跳过 |
| `server.js` 路由 | 真实端口集成测试:`/report` 写入后可被 `/api/records` 读到;`since` 增量;`/api/export.csv` 的 BOM 与转义 |
| 看板页面 | **无自动化测试**,靠浏览器实测(见风险) |
| 脚本上报 | **无自动化测试**;靠浏览器实测确认「上报不影响主流程」与「数据正确落盘」 |

## 10. 不在本次范围内

- 图表统计(通过率、规模/薪资/城市分布)
- 历史记录的编辑与删除
- 多机同步、鉴权(仅监听 `127.0.0.1`)
- 同一岗位的重复上报去重 —— 同一岗位在不同轮次被重复判定是**事实**,应如实记录多行
- 对既有 IndexedDB 数据做历史回填(从本功能上线开始记录)

## 11. 风险

1. **看板页面与脚本上报都没有自动化测试。** `ledger.js` 和路由有单测覆盖,但"页面渲染是否对"和"上报是否真的不影响主流程"只能靠浏览器实测。因此实现阶段必须由用户实际跑一轮确认,不能以"单测全绿"结案。
2. **上报增加一次网络往返。** fire-and-forget,不阻塞;但服务端若长时间无响应,浏览器会积压连接。用短超时(5 秒)规避。
3. **JSONL 无限增长。** 秋招全程预计量级在千行以内,不构成问题;不做轮转。
